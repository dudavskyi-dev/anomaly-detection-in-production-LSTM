This is exactly the pattern the spec calls out: FD001 and FD003 run under a single operating
condition, so `op_setting_3` and several sensors that only respond to operating condition (not
fault progression) are true constants there. FD002 and FD004 run under six operating conditions,
so those same columns have large *global* variance — not because they carry more fault signal,
but because the six-condition mixture dominates the raw variance. **This is not yet handled**:
P01 only profiles the raw subset; per-condition normalisation (clustering the six conditions and
computing constancy *within* each) is P02's job, using this exact profile as its starting point
rather than re-deriving or guessing it. Naively concluding "FD002/FD004 have no constant sensors"
from this table alone would be a mistake — see the note in `docs/SPEC.md` §6.1 this log is
flagging forward to P02.

Full per-column std for every subset is in
`data/processed/cmapss/sensor_profile.json` (regenerated by `make data`, not committed — it's
fully reproducible from the raw data, so a git diff would just be noise).

## Parsing surprises

- **The nested zip.** The NASA S3 URL serves an outer zip containing a *single* inner zip,
  `CMAPSSData.zip`, which itself holds the flat `train_FDxxx.txt` / `test_FDxxx.txt` /
  `RUL_FDxxx.txt` files (plus a readme and a PDF). `cmapss.py` extracts the inner zip's bytes
  into memory (`zipfile.ZipFile(io.BytesIO(...))`) rather than writing an intermediate file to
  disk — there's no reason to round-trip through the filesystem twice for a 12 MB archive.
- **Trailing whitespace.** Every line in the raw text files ends with two trailing space
  characters (verified directly on the downloaded file). A hand-rolled `line.split(" ")` would
  produce a phantom 27th field; `pandas.read_csv(..., sep=r"\s+", engine="python")` treats
  runs of whitespace (including the trailing run) correctly and needed no special-casing beyond
  choosing that separator over a literal `" "`.
- **RUL file ordering.** `RUL_FDxxx.txt` has no unit-id column — it's positional, one value per
  test engine, and the C-MAPSS documentation doesn't explicitly restate the ordering convention
  in the file itself. `attach_true_test_rul` assumes the values are in ascending unit-id order
  (matching the order engines first appear in the corresponding `test_FDxxx.txt`) and asserts
  the value count matches the unit count before mapping — if that assumption is ever wrong for
  some subset, this raises loudly (`ValueError: RUL file has N values but test set has M units`)
  instead of silently mis-attaching RULs to the wrong engines.

## Why parquet

Columnar storage, typed schema round-trips exactly (no CSV re-parsing/re-inferring dtypes on
every load), fast reads for the windowing step in P02, and native support in both pandas and
(later) any Spark-less batch tooling without extra dependencies beyond `pyarrow`, which was
already a core dependency from P00.

## What validation caught

The pandera schemas (`pdm/ingestion/schema.py`) were exercised against the real downloaded data
during development, not just the fixtures: an early version of `parse_run_text` before the
`.astype(int)` calls on `unit`/`cycle` let pandas infer `float64` for those columns (harmless
for compute, but semantically wrong — a cycle number is a count, not a measurement), and
`cmapss_schema()`'s `Column(int, ...)` requirement caught it immediately during manual testing,
rather than it surviving into P02 as a subtle dtype trap. The custom
`_check_cycles_start_at_one_and_are_contiguous` check (not expressible as a single-column
pandera `Check`) also caught a version of the test-set profiling code that computed
`cycles_per_unit` from the wrong dataframe during development.

Beyond the schema itself, `attach_true_test_rul`'s length assertion is a second, deliberate
validation layer: if a future C-MAPSS mirror ever changes the RUL-file format, this fails loudly
at ingestion time rather than producing a silently-misaligned label three milestones later.

## Label leakage (AI4I)

`twf`, `hdf`, `pwf`, `osf`, `rnf` are validated and written to `data/processed/ai4i.parquet`
**unmodified** — P01 does not drop them. `machine_failure` is defined as the logical OR of
those five flags, so including them as model features would let a model "predict" failure by
reading the flags that define failure, rather than learning from the underlying sensor readings
(temperature, speed, torque, tool wear). Dropping them is P02's explicit, tested step
(`tests/test_leakage.py` will assert their absence from the feature matrix); P01's job is only
to get the raw data faithfully into parquet.

## Other decisions

- **AI4I fetch path**: `ucimlrepo.fetch_ucirepo(id=601)` is tried first (used successfully in
  this run — no fallback needed). The direct-CSV fallback (`_fetch_via_csv_fallback`, from the
  UCI static export URL) exists and is exercised only if `ucimlrepo` itself raises; both paths
  are real data sources, not synthetic substitutes, matching the spec's "prefer X, fall back to
  Y" instruction. AI4I's raw dataframe is re-exported to `data/raw/ai4i/ai4i2020.csv` specifically
  so the manifest has a concrete file to hash and the idempotency check has something to compare
  against on the next run — `ucimlrepo` itself exposes no ETag or hash of its own.
- **NAB windows representation**: labelled anomaly windows are stored two ways — as a boolean
  `is_anomaly` column merged into the main parquet (convenient for per-row metrics), and as the
  original `[start, end]` timestamp pairs in `data/processed/machine_temperature_windows.json`
  (needed later for NAB's own window-based scoring, which differs from point-wise F1 — P06 will
  need both representations).
- **Manifest caching**: a single `data/raw/manifest.json`, keyed by destination path, records the
  SHA-256 and byte count of every downloaded file. `pdm data download` run twice in a row
  completed in under 10 seconds the second time (vs. needing to fetch a 12 MB zip, a CSV, and
  two NAB files the first time), confirming no unnecessary re-download.
- **Replay noise scope**: the replay simulator (`pdm/ingestion/replay.py`) only perturbs
  float-dtype columns with Gaussian noise, deliberately excluding integer columns. This was
  caught during manual testing — the first version applied noise to every numeric column
  indiscriminately, which corrupted AI4I's integer failure-mode flags and `machine_failure`
  label into meaningless floats (e.g. `machine_failure: -2.68`). Real sensor noise applies to
  continuous measurements, never to binary flags or unit/cycle counters, so the fix restricts
  `noise_std` to `df.select_dtypes(include="float")`.

## Environment note

An unrelated but real problem surfaced while wiring the `pdm data replay` CLI command: `typer`
(pinned `~=0.12.0` in P00) crashed on any usage error with
`TypeError: TyperArgument.make_metavar() takes 1 positional argument but 2 were given`, because
nothing pinned `click` and pip resolved `click==8.5.0`, whose `8.2` line changed the
`make_metavar` signature typer 0.12.x's compatibility shim doesn't expect. Fixed by pinning
`click~=8.1.0` explicitly in `pyproject.toml` core dependencies. Lesson: a library that wraps
another library's plugin/extension points (typer wrapping click) needs that dependency pinned
explicitly too, not left to whatever the resolver picks — the "pin major versions" rule from P00
should have included click from the start.

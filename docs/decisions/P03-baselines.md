## Strongest baseline, and why

**RUL regression**: `random_forest` (test RMSE 15.37 vs ridge's 16.95). Hypothesis: the feature
set is 595-dimensional (30-step flattened window × 17 sensors, plus 5 summary stats × 17
sensors) with heavy redundancy and non-linear sensor/degradation relationships; a tree ensemble
can pick out informative interactions and thresholds that a linear model's L2 penalty spreads
weight across instead of concentrating on. The gap (~10%) is real but not enormous — this is a
case where P04's LSTM has real room to beat both by learning the *temporal* structure directly
rather than from hand-flattened summary statistics.

**Failure classification**: `random_forest` and `logistic_regression` are statistically
indistinguishable (test PR-AUC 0.917 vs 0.916, well within a std of each other). Hypothesis: near
failure, degradation signal is strong and close to linearly separable in this engineered feature
space (the summary-stat features especially — a sensor's trend slope over the last 30 cycles is
already a strongly discriminative, roughly-linear signal for "about to fail"), so RandomForest's
non-linearity buys almost nothing here. This is itself informative: it says the *feature
engineering*, not the classifier, is carrying this task, and sets a real, high bar (PR-AUC ≈ 0.92)
for P04/P06 to clear with less hand-engineering.

**AI4I**: `random_forest` clearly beats `logistic_regression` (val PR-AUC 0.650 vs 0.423) — the
opposite pattern from the C-MAPSS classifier. Hypothesis: AI4I's failure modes are genuinely
non-linear interactions (e.g. high torque **and** high tool wear, or specific combinations of
temperature and speed per the dataset's known physical failure-mode definitions), which a linear
model with only 5 numeric + one-hot `type` features can't capture, while a tree ensemble can.

## What the dummy/linear/tree gap says about signal in the data, before any deep learning

- **RUL regression**: dummy_mean's test RMSE (37.9) and dummy_cap's test RMSE (36.2) are close to
  each other but *catastrophically* different on NASA score (363k vs 15.78M) — see the callout
  below. Ridge alone cuts RMSE from ~37–38 down to 16.95, a ~55% reduction, before any tree or
  deep model. That's a large amount of real, linearly-extractable signal already present in raw
  windowed sensor values; the remaining ~10% gap RF closes, and whatever P04's LSTM closes beyond
  that, is a much smaller and harder-won improvement. A headline claim like "LSTM achieves RMSE 16"
  would be nearly meaningless without this table — Ridge is already at 16.95.
- **Failure classification**: dummy's PR-AUC (0.033 test) sits essentially at the test-set
  positive rate itself (see below); logistic regression alone reaches PR-AUC 0.916 — almost all
  of the achievable signal is linear and already captured by the simplest real model. This
  strongly suggests P04/P06 should be judged on *robustness, calibration, and not needing
  hand-engineered summary features* rather than on raw PR-AUC headroom, since there isn't much
  headroom left above 0.917.
- **AI4I**: the gap between logistic regression (0.423) and random forest (0.650) shows this
  dataset's signal is real but genuinely non-linear — a case where "the classical baseline" is
  itself two very different numbers depending on which classical model, which is worth knowing
  before citing "a classical ML baseline" as a single, undifferentiated fact.

## The dummy_cap trap: a real, measured illustration of why RMSE alone is dishonest here

`dummy_cap` (always predict RUL = 125, "assume every engine is perfectly healthy") has a test
RMSE of **36.18** — actually *better* than `dummy_mean`'s 37.91. Judged by RMSE alone, "assume
nothing is ever wrong" looks like a perfectly reasonable baseline. Its NASA score is
**15,783,249.66** — roughly 350× worse than dummy_mean's 363,066.82, and about 370× worse than
Ridge. The reason: NASA's asymmetric score penalises *late* predictions (predicting more life
remains than truly does) exponentially, and predicting 125 for an engine with true RUL 0 is
about as late as a prediction can be. This is the single clearest, most concrete demonstration
in the whole project so far of why RMSE and NASA score can disagree, and it happened on real
data without any deliberate engineering to produce it.

## PR-AUC vs ROC-AUC on this class balance, with both numbers

C-MAPSS failure-within-30-cycles: **train/val positive rate ≈ 17.7%/16.8%**, but **test positive
rate ≈ 3.26%** (measured directly from `prepare_cmapss_subset("FD001", ..., seed=0)`) — test
engines are truncated at an arbitrary point before failure (via the `true_rul` offset from P01),
so far fewer of their windows land within the last 30 cycles than for train/val engines, whose
full run-to-failure trajectories are windowed completely. This matters for reading the table
correctly: dummy's ROC-AUC is exactly 0.500 on both val and test (an uninformative classifier is
uninformative regardless of prevalence — ROC-AUC doesn't move), but dummy's PR-AUC drops from
0.179 (val) to 0.033 (test), tracking the positive-rate drop almost exactly. **PR-AUC is
prevalence-sensitive by design** (it's answering "of the windows flagged positive, how many
really are," which gets harder as positives get rarer), while ROC-AUC is not — which is exactly
why PR-AUC is the honest headline metric here: it reflects that the real-world operating
condition (test, ≈3% positive) is a harder, more imbalanced problem than the validation split it
might be tempting to report from.

A second, more subtle consequence: a max-F1 threshold chosen on validation (≈17% positive) is
being applied to a test set with a very different base rate (≈3%). Despite that, PR-AUC held up
well (0.917 test) — the score *ranking* generalises even though the base rate shifted, which is
the right thing to check before trusting a threshold across a distribution shift like this.

## Threshold selection: the worked example (seed 0, random_forest, FD001)

- **Max-F1 threshold** (validation): 0.5536, achieving F1 = 0.915 on validation.
- **Threshold at ≥90% precision** (validation): achieves 92.3% recall while holding ≥90%
  precision — meaning at this operating point, roughly 1 in 10 flagged engines is a false alarm,
  but over 92% of engines that will actually fail within 30 cycles get flagged.
- The `dummy` baseline **cannot** reach 90% precision at any threshold on validation
  (`threshold_at_precision` raises `ValueError`, caught and recorded rather than crashing the
  run) — its only real operating point (predict-everyone-positive) tops out at the base rate,
  ≈17.9% precision on validation.

**Which to ship**: the precision-constrained threshold (recall 92.3% @ precision ≥90%), not the
max-F1 threshold, for a maintenance use case — a missed failure (false negative) risks real
equipment damage or safety exposure, while a false positive only costs an unnecessary inspection.
92.3% recall at 90% precision means roughly 1 false alarm per 9 correct flags, which is a
plausible number of "please go check this engine" tickets before alert fatigue sets in; buying
more recall by dropping precision further would need to be justified against how many false
alarms the maintenance team can actually absorb per week, which is outside what this dataset can
tell us on its own.

## The evaluation framework: what got built and why

- **`evaluation/metrics.py`**: every classification metric sklearn computes here is checked in
  `tests/test_evaluation_metrics.py` against `precision_recall_f1_from_confusion`, a hand-derived
  reference with no sklearn dependency. The NASA score is checked against hand-picked values
  where the early/late asymmetry is visible by construction (`d=-13` and `d=+10` both score
  `exp(1)-1` individually, but the same-magnitude `d=±20` case shows late costs more).
- **`evaluation/thresholds.py`**: every function takes a required `split` keyword with no
  default, so a threshold computed on the wrong split is a `TypeError`/`ValueError` at the call
  site, not a silent mistake. See "a performance bug hit" below for why this module's internals
  changed shape after the first implementation.
- **`evaluation/harness.py`**: `Split`/`evaluate()` structurally enforces "test is scored once
  per experiment" — a `Split(name="test", ...)` raises `SplitAlreadyEvaluatedError` on a second
  `evaluate()` call against the *same instance*. The baseline runner builds a fresh `Split` per
  seed (a new, independent final measurement), so 5 seeds means 5 single-use test evaluations,
  never the same test predictions scored twice.
- **`evaluation/stability.py`**: `run_seeds`/`aggregate_over_seeds` are the only place mean/std
  aggregation happens; every number in `docs/RESULTS.md` traces back through these two functions.

## Problems hit and how they were fixed (the richest part of this log)

**Bug 1 — `RandomForestRegressor`'s hidden slow default.** The very first RUL-regression baseline
run didn't finish in 20+ minutes and was killed. Investigation (`Get-CimInstance Win32_Process`,
watching CPU/working-set) showed a joblib worker process actively burning CPU, not a hang. The
cause: `RandomForestRegressor`'s default `max_features` is `1.0` (consider **every** feature at
every split), unlike `RandomForestClassifier`'s default of `"sqrt"` — an easy default to miss,
and disastrous with 595 engineered features. Setting `max_features="sqrt"` explicitly (now the
default for every baseline RF, regressor and classifier alike, via
`settings.training.baseline_rf_max_depth`/`baseline_rf_n_estimators`) brought the same run down
to **70 seconds**. Also added an explicit `baseline_rf_max_depth=12` while investigating, both
recorded in config rather than left as library defaults.

**Bug 2 — an O(n × unique_scores) threshold sweep.** The first `thresholds.py` implementation
looped over every unique observed score and recomputed a full confusion matrix
(`classification_metrics`, four separate sklearn calls) for each candidate — fine on the tiny
unit-test fixtures, but on ~3,272 real validation rows with mostly-unique continuous scores, that
loop plus its four O(n) sklearn calls per iteration made the failure-classification baseline run
never complete either. Rewritten to use `sklearn.metrics.precision_recall_curve`'s single
O(n log n) sorted pass to find the best/target-precision threshold, then call
`classification_metrics` **once** at the chosen threshold for the full metrics dict. Brought the
same run down from never-finishing to **47 seconds**. `tests/test_evaluation_thresholds.py`
passed unchanged before and after — same public contract, verified equivalent, just no longer
quadratic.

**Bug 3 — Windows text-encoding corruption of `±`.** `docs/RESULTS.md` initially rendered `±` as
`�` — not a terminal display glitch but real data corruption: `pathlib.Path.write_text()` /
`.read_text()` default to the platform locale encoding when no `encoding=` is given, which on
this Windows machine is not UTF-8. Every `write_text`/`read_text` call across `pdm/` (JSON
manifests, `scaler.json`, `feature_spec.json`, `sensor_profile.json`, `docs/RESULTS.md`) now
passes `encoding="utf-8"` explicitly, even where current content happens to be ASCII-only —
relying on "it's ASCII so it doesn't matter today" is exactly the kind of assumption that breaks
the next time someone's name or a µ/± shows up in a value.

## No test-RUL-offset bug this time either

Failure-classification and RUL-regression baselines both reuse P02's `prepare_cmapss_subset`,
which already applies the correct `add_rul_test` offset — no new offset logic was written here,
so there was nothing new to get wrong. The positive-rate discrepancy documented above (17.7%
train/val vs 3.26% test) is a genuine property of the labelling, not a bug — verified by
recomputing `will_fail` rates directly from the pipeline output rather than assuming it.
